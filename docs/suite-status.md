# Suite status

One line per `scripts/run-unit-suite.sh` run, appended by the script itself —
nothing else may write here. Red runs are recorded too.
`./scripts/run-unit-suite.sh --last` prints the newest row and how many commits
HEAD has moved since it.

This file is an instrument reading, not documentation. A row means a suite run
happened; the only thing entitled to say so is the thing that ran it. A hand
edit here is a blocking review finding unless the item is about this recording
mechanism — see the reviewer rubric in `CLAUDE.md`. The rule dates from
2026-08-11, when a worker on an unrelated item typed in a row nobody had
measured; the story is told in
[autonomy.md](autonomy.md#never-write-the-suite-record-by-hand).

The result bundle cell is the bundle xcodebuild wrote for that run — named from
the wall clock when testing started, and present on disk only because a build
ran. It is the cell you cannot type, so a row nobody measured is the row whose
bundle is nowhere:

```bash
find ~/Library/Developer/Xcode/DerivedData -name '<the cell>'
```

The failing tests cell names the tests that failed. A count told you the tree was
red and nothing about what was red, and the names lived only in a temporary log
the script deletes on its way out — so learning them meant running the suite
again.

The last cell names the tests that skipped, for the same reason the cell before
it names the ones that failed. `(1 skipped)` in the tally says how much of the
suite opted out and nothing about which part of it did, and the two are not
interchangeable: 47 XCTSkip sites live in `KiteloopTests`, most of them
conditional on a free loopback port for the control server and two on an
installed `claude` binary. So one row's skip is an expected opt-out on a busy
machine and the next row's is a control-server endpoint whose coverage went
missing — the same eleven characters either way. Only XCTest's skips are named,
because only XCTest's are counted: swift-testing's summary reports none.

Either cell is a dash when there were none, and the names in both are spelled the
way `-only-testing:` takes them, so one can be pasted straight into a narrowed
re-run.

On a row whose tally says the run was ended at its time limit, the failing tests
cell names the tests that were still in flight when the ceiling fired — cases
that started and never came back, which is what that run hung on. Nothing failed
on such a row, so `--last` prints those names under `hung` rather than `failing`.
It is a dash when the ceiling fired before any test had started.

The duration cell is how long the run took, in seconds — the wall clock from the
moment before xcodebuild starts to the moment it returns. Every other cell says
what the run found and none of them said what it cost, so "how long does the
suite take, and is it getting slower?" was answerable only from somebody's
memory of the last time they watched it scroll. Seconds rather than a `4m 14s`
phrase because two rows get compared far more often than one gets read alone.

The last cell is `Kiteloop/KiteloopCore`'s own tally — the host-less package's
tests, run under `swift test` by that run's `scripts/run-core-tests.sh`
preflight entry rather than by xcodebuild, which never builds that package's
tests at all and so never counted them in the tally cell above. Without this
cell a test moving out of `KiteloopTests` and into the package read as a test
lost rather than a test relocated: the tally cell fell across several rows in
2026-08-23 while nothing was deleted, because that is exactly what was
happening. Read from the `OK: KiteloopCore — …` line that preflight entry
prints for itself, a dash when that run named no tally of its own.

The rows below were written as the columns arrived, so older rows simply run
out of cells, and nothing is back-filled: a cell nobody measured would be a
reading nobody took. `--last` omits a line for a cell a row does not carry
rather than showing an empty field.
